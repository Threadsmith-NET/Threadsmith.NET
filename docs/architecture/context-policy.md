# Context Policy

Threadsmith.NET assembles each model request from explicit state and bounded conversation continuity. The model-context order is request-owned provider instructions when present, stable host policy, the applicable repository instruction/append bundle, canonical native tool definitions, stable conversation instructions, additional prefix instructions, recent complete exchanges, included repository memories/preferences, governed task/state/evidence/output requirements, current user input, and admitted continuation messages. Native tool definitions and provider instruction/schema fields remain separate request fields where the transport supports them, but their JSON property positions do not define model-context order. See [ADR-41](adr-41-canonical-cache-optimized-model-requests.md) and [request-order operations](../operations/cache-optimized-context.md#request-order). `/context map` reports final prepared request accounting in that host-owned order, while `/context inspect` retains assembly and reduction diagnostics.

## Ordinary conversation evidence

Repository maps, source excerpts, semantic facts, tool results, user constraints, accepted decisions, diagnostics and failures are eligible through the shared evidence policy. No planning-phase or approved-plan gate controls evidence admission.

Within an eligible set, accepted decisions are selected first, then relevance, recency, and stable evidence id. Stale items are excluded. Duplicate content keeps its strongest item. Provisional evidence admission is bounded by the largest configured profile input capacity so a legacy global ceiling cannot discard evidence before model selection. Threadsmith then resolves the request's selected model once and reduces the final request to that profile's configured context window minus its configured maximum output-token reserve. Evidence that would exceed this per-model budget is omitted rather than truncated. The context inspector records every decision, token estimate, selected-model window, output reserve, and effective input budget. There is no shared `context:maxTokensPerRequest` cap across models.

Invalidations are queued when repository or semantic state changes, after applied mutations (including both move paths), and after rollback, then applied before the next assembly. File dependencies retain normalized paths, ranges, invocation provenance, and available SHA256 identities; all declared dependencies participate in invalidation. Change timestamps protect later reads from delayed event delivery. Admission indexes non-stale dependencies by session and path, superseding older differing file versions while preserving complementary ranges of the same version. Historical evidence remains inspectable. Source dependency metadata does not require membership in a mutation baseline and does not grant write authority. Project append files are re-read and content-hashed at the same boundary.

Model resolution uses the requested workload, required capabilities, sensitivity, cost constraints, and configured profiles. Advisory hints are snapshotted at the boundary. Invalid or incompatible hints are ignored with a recorded reason; an explicit user/session default takes precedence.

Ordinary conversation context uses stable host instructions, advertised capabilities and bounded evidence. Source-edit receipts and advisory diagnostics enter through normal tool results and provider-compatible continuations. Evidence provenance, freshness, replay and capacity checks remain enforced.

## Delegated child context

Plan-38 children receive a separate bounded `AgentContextSnapshot`: frozen objective/tasks/output contract, immutable parent baseline identity, role-eligible governed evidence, and the intersection of parent/assignment tools. Parent/sibling transcripts, hidden reasoning, unrelated conversation memory, and mutable sibling outputs are excluded. Dependency output can enter only after a durable join as schema-valid evidence. Explorer findings must cite evidence already admitted by the parent; accepted projections add child-run, assignment, model-profile, baseline, location, confidence, and invalidation provenance before later parent assembly.

## Skill procedure context

Plan-39 catalog discovery contributes metadata only. After explicit immutable selection, verification, enablement, compatibility, and schema validation, the skill loader reads only the current workflow step's declared instruction/schema/reference assets. Every segment is path-confined, hash-rechecked, strict-UTF-8 decoded, sanitized, token-counted, and tagged with scope/id/version/digest, step, asset path/hash, and required/optional status. Required content pressure fails; optional references omit deterministically. Skill segments remain untrusted procedure data below stable host policy, repository rules, trust, tool and host contracts, and governed evidence. Parent/sibling transcripts, hidden reasoning, unrelated skill bodies, signer keys, and raw provider/tool payloads are excluded.

## Repository intelligence context

Intelligence is untrusted advisory memory in the shared repository store, with its own ownership-filtered recall policy and inclusion count. It participates only after explicit onboarding while effectively enabled, under ordinary sensitivity, tool-policy and context-capacity checks. It never receives standing-preference authority. Supporting paths and changed/unknown evidence warnings enter the actual request and frozen context inspector; a warning does not veto recall. Current source overrides stale assertions, and enabled-only guidance asks the model to clarify apparent task conflicts with the user.

Source observation runs in the background. Assembly and final dispatch read only lightweight eligibility and stored memory metadata; they do not wait for scanning or verify source contents. Metadata, configuration and effective fault/disable transitions invalidate retained intelligence and enabled-only prose through existing request reconstruction and provider-context invalidation before the next actual request. Already submitted requests remain unchanged. Ordinary-only memory refresh keeps its existing continuation snapshot behavior.

`MemoriesIncluded` reports only actual submitted additions, using the shared Memory renderer with terminal-control encoding. The global output toggle never removes inspection data from the request snapshot. See [ADR-59's intelligence amendment](adr-59-model-managed-repository-memories.md#repository-intelligence-amendment-2026-10-11).
