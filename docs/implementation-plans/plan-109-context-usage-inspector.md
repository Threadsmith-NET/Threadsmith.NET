# Plan 109 — Ordered context usage inspector

**Status:** Implemented on `codex/plan-109-context-usage-inspector` — automated verification and adversarial review complete; physical-terminal MTP-271 verification remains outstanding. See section 18 for evidence and limits.
**Delivery track:** Maintenance — extend existing context inspection, request accounting, and retained TUIKit presentation.
**Prerequisites:** Implemented governed context and inspection, canonical request preparation (ADR-41), active-turn continuation/compaction, shared interaction coordination (Plan 98 / ADR-51), retained TUIKit and agent workspace (Plans 100 and 105 / ADR-52), and current provider capacity/replay contracts (including ADR-60). Plans 106, 107, and 108 are not prerequisites.

## 1 Objective

Add `/context map`, a read-only context-usage inspector answering: **“Why is my context usage so high?”** Double-clicking the Context usage meter at the top-right of MAIN's output window invokes the same functionality. Display the latest actual primary-agent request's components in their real request order, with individual source sizes and a sidebar of total usage and aggregate category shares. Users must be able to identify a large `AGENTS.md`, appended prompt, tool definition, memory, message, or tool result and decide whether to change it through existing workflows.

Use native TUIKit graphing widgets in a larger modal. The left pane preserves request order; the right pane makes the largest categories obvious. Opening, navigating, and closing the inspector must not assemble a prospective request, invoke a model, run tools, retrieve memories, reload instruction files, or alter context.

The user's examples establish the kinds of content to explain, not a presentation ordering. There is no conceptual-order alternative and no next-request preview.

## 3 Scope

- `/context map`, a double-click entry on the top-right Context meter, command discovery/help, retained large modal, and a text fallback for the original frontend.
- One immutable snapshot of the latest prepared primary-agent request from normal execution, including subsequent tool/correction continuations and the request after compaction.
- Ordered component attribution, per-source sizes, complete category totals, selected-model window, estimated input usage, and estimation basis.
- System and phase prompts, included append files and applicable repository instructions, actual eligible tool schemas, included memories/preferences, conversation, task/governed state, evidence, output contracts, injected skill/host instructions, summaries, and provider overhead/replay where present.
- Shared request identity and accounting between the inspector and primary-agent context indicator.
- Native TUIKit `BarChart` and `ProgressBar`, flat source navigation, scroll/resize behavior, bounded metadata, and integration/regression coverage.

## 4 Non-Scope

- Next-request previews, hypothetical tool/prompt changes, conceptual reordering, model analysis of usage, recommendations generated by a model, or historical usage dashboards.
- Editing instructions, disabling tools, modifying memories, triggering compaction, exporting prompt content, or viewing raw prompts/reasoning from the modal.
- A new child-agent selector or child-tab command execution. Existing primary-agent command ownership remains intact; child activity cannot contaminate this snapshot.
- Replacing current estimators, introducing exact tokenizers, changing admission limits, or treating billed/cumulative tokens as current context occupancy.
- New instruction-file discovery rules, a new tool registry, loading dormant skill bodies, or counting all stored memories/history as included context.
- Provider SDK or TUIKit types in Core/public projections; new packages or a TUIKit upgrade merely for this feature.
- Staging, commits, publishing, destructive Git operations, or unrelated cleanup.

## 6 Proposed Design

### 6.1 Command and snapshot semantics

Add `/context map` to the existing context command family. The command targets MAIN's current session and latest primary request through shared interaction coordination, not the selected child tab. Preserve existing child-input restrictions and existing `/context`, `mode`, `inspect`, and retired `compact` behavior.

Double-clicking MAIN's Context usage meter is an equivalent entry into that same command action, snapshot query, and modal lifetime. Route a host-owned interaction action through existing coordination; do not insert or submit `/context map` as composer text, overwrite a draft, or implement a second frontend-only query/open path. Preserve command telemetry and cancellation, with at most one invocation and modal per gesture. It must work while ordinary execution is active without becoming steering or a model-visible message. The gesture retains this plan's primary-agent scope: a child meter must not silently open MAIN's unrelated accounting.

“Current” means the latest request actually prepared by the normal primary execution path, including a continuation or mutation/proposal request. Label the modal `Context usage` and identify model, request/round, and capture time in a compact subtitle. It is a captured request, not a prediction of the next request or all durable session content. A newly generated response only counts when it is included in a subsequent request.

Reuse the existing host request/invocation identity and purpose classification; extend them minimally if needed. Record whether a prepared request proceeded to provider submission or failed/cancelled beforehand without claiming preparation proves submission. Never publish speculative capacity candidates as the current snapshot.

Separate auxiliary compaction-generation calls from the primary context they summarize. Those calls must not replace MAIN's context map or its matching context indicator; cumulative usage still accounts for them normally. Children remain independently owned. Update the existing status projection/observation as needed to make this distinction explicit rather than introducing a second latest-request store.

Opening freezes one immutable snapshot for the modal's lifetime. Execution continues through its existing path. Later requests do not reorder rows while a user is reading; reopening obtains the newest snapshot. No timer, automatic refresh, additional request-history store, or preview is required.

Before a request exists, after unavailable/evicted metadata, or following resume without suitable transient metadata, show a concise unavailable reason. Do not reconstruct a request from the database, guess a model window, or display unknown values as zero. If configuration changes after capture, retain the captured model/limit and timestamp in the inspector until a new actual primary request replaces it. MAIN's header identity follows the current selected model/reasoning immediately; that selection is distinct from captured request metadata. After a model switch, the header shows unknown occupancy for the newly selected model until a request is prepared. Do not reintroduce stale model/reasoning labels to make the header match a historical snapshot.

### 6.2 Ordered provenance

Capture source attribution while existing assembly functions already have the sanitized, bounded, included content. Keep occurrence identity separate from reusable source identity: two messages with the same section ID occupy two positions. Carry this host-only attribution alongside canonical messages through normal continuation, reduction, and provider preparation.

Each displayed contribution needs a stable occurrence ID, category, safe display label, source identity/path when available, transport container, ordinal, and estimated token contribution. Internal accounting may retain parent/child relationships; both frontends display only the flat, nonzero contributions, without parent totals. Keep request identity, timestamp, model window, reserve, total, and estimation basis at snapshot level.

Preserve the final prepared message/block order and order within source bundles/tool inventories. Provider adapters that merge messages or move initial instructions must preserve the attribution mapping through their existing projection. Separate native fields (instructions, tools, response format) are labeled as separate request fields, with their actual internal order. Do not portray JSON property order as a provider's hidden prompt order. Where the provider does not expose a linear ordering between fields, show the fields explicitly alongside the ordered message stream and state that boundary briefly.

The left pane is a flat top-to-bottom stack in prepared-content order. A category occurring in several places stays in those places; only the right pane aggregates it into larger groups. Do not display nested groups, collapse/expand controls, parent totals, or empty entries.

### 6.3 Categories and individual contributors

| Category | Attribution rules |
|---|---|
| System prompt | Stable host system policy; preserve any separate request-owned provider instruction field as its own labeled component. |
| Appended prompts | One source entry per included configured append, preserving real placement. |
| Repository instructions | Each actually included hierarchical instruction source. Deduplicated sources count at their surviving occurrence only. |
| Tools | Actual native or text-transport definitions: tool name, description, and schema. Expand to individual names, with native/MCP provenance when already available. No count for tools excluded by the request's authority/snapshot. |
| Memories | Only included repository memories and standing preferences, labeled by safe ID/type rather than full memory text. |
| Conversation | Included historical/current messages and active-turn assistant/tool-call/tool-result content. Show role and sequence/tool identity; do not load/display the full body. |
| Phase instructions | Existing phase policy as a named component. |
| Task and governed state | Task/acceptance facts, plan/baseline/state payloads actually present. |
| Evidence | Included evidence with safe source labels, including joined child findings only where admitted into the primary request. |
| Compaction summary | Active included summary; replaced raw groups no longer contribute. |
| Additional instructions | Included skill, steering, or other host-provided content, using available provenance rather than guessing from text. |
| Output contract | Included required-output instructions and separately transported response schema. |
| Provider overhead/replay | Serialization/framing, opaque retained content, and conservative allowances that cannot be attributed to visible sources. Break these into named contributions where the adapter can distinguish them. |

Classify each included occurrence once. Tool results in a conversation count there, not again as tool definitions; evidence copies count as evidence only when separately included. Content repeated in the actual request genuinely consumes space twice and must remain visible. A parent total summarizes its children and never adds another contribution. Hide absent categories; unavailable attribution is not an absent category.

### 6.4 Consistent accounting

The headline is the final provider-aware input estimate used for this request. The sidebar shows `Input: N tokens`, `Window: W tokens`, and `Used: N / W percent`. Category shares use `category / N`, with the heading `% of input`. Keep the output/reasoning reserve as a small separately labeled capacity value; it is not included input and must not appear as another context-content category.

All displayed numbers must use one estimation basis for the captured request. Neutral four-character estimates cannot be added directly to another adapter's byte-based estimates. Extend each shipped preparation path's metadata using the content/projection it already constructs. Do not reinterpret its present `SectionTokens` blindly, change admission algorithms, or serialize full payloads just for the UI.

Required invariants:

1. Non-overlapping leaf contributions sum to category totals; category totals sum to displayed input.
2. Whenever the context indicator shows measured occupancy, it and the inspector use the same primary request identity, total, and captured model window. A selection change alone does not create a new request; the model-switch unknown state described in section 6.1 remains valid.
3. Wrapper/escaping and rounding contributions are deterministically attributed or explicitly recorded as overhead. Do not force reconciliation by adding a negative residual, scaling unrelated categories, or silently clamping inconsistent totals.
4. Native/text tool transport, provider instructions, response schemas, and retained private replay count once in the appropriate final representation.
5. If exact source subdivision is unavailable, retain the known parent amount and label its unallocated portion. Do not fabricate per-source precision. Shipped visible append/instruction/tool contributions are required, not optional unallocated buckets.
6. Percentages handle zero/unknown denominators, use overflow-safe arithmetic, and disclose ordinary display rounding. A nonzero tiny item can show `<0.1%`.
7. Cache hits do not subtract context occupancy. Provider-reported or cumulative usage does not replace category estimates or imply exact per-category tokenization.

Label the view `Estimated` and provide a short basis description, such as `Conservative provider capacity estimate`. Retained hidden/reasoning content has size-only attribution; never expose its bytes or imply that its size is editable prompt text.

### 6.5 Native charts and modal geometry

Use TUIKit 0.10.1 `BarChart` for the ordered left breakdown and the right category summary, and `ProgressBar` for input/window usage. Reuse existing theme roles and status styling. These native widgets are an implementation requirement; do not substitute hand-drawn bars or introduce another graphing library.

- Left: roughly two-thirds of the inner width, readable labels, token values, native bars, and a flat stack of individual source contributions in prepared order. Show instruction files, appended prompts, tools and conversation contributions directly, omitting zero-size entries and parent totals.
- Right: fixed during left scrolling, total/window/percentage, capacity progress, then category bars sorted descending by tokens with deterministic tie order and numeric category shares. Sidebar totals retain the larger category groups and never depend on the viewport.
- TUIKit bars are relative to the largest entry, not the full model window. Make that distinction clear through labels/numbers; only the overall progress bar expresses window utilization. Preserve a stable comparison scale while scrolling a fixed dataset. All source rows use the same indentation; accounting parents are omitted.
- Bound long labels and sanitize control characters. A selected-row detail line can show its full bounded source path/tool name and size; no raw content browser is needed.
- Add an opt-in large preset to `ModalFrame`, initially targeting up to 140 columns by 40 rows while retaining normal outside margins. Existing modal default geometry remains unchanged.
- Use side-by-side panes when they fit; at narrow widths put summary above the scrollable detail. At very small supported dimensions provide readable compact content or a resize message instead of an invisible dialog.
- Up/Down, PageUp/PageDown, Home/End navigate; Tab switches ordered contributions/category ranking; Esc closes. There are no expansion controls. Preserve the existing Ctrl+C interrupt, F12 mouse, focus, draft, and modal lifetime semantics. Support wheel scrolling through the existing mouse-capture path where available.
- Make the rendered top-right meter's entire area (Context/Ctx label, bar, percentage, and capacity) the double-click target, including its compact summary-only form. Derive hit bounds from the same header layout used to render it, recomputing after resize; do not duplicate width arithmetic in the mouse handler. Use TUIKit's synthesized `MouseEvent.ClickCount` through the existing mouse route for a left-button double press. Single clicks, other buttons, dragging, clicks outside the meter, and a third click must not open another inspector. Respect F12 mouse-capture state and modal/startup input ownership. An unavailable meter invokes the same unavailable response as `/context map`.

Inspect native chart clipping/measurement before coding. Keep composition, selection, scrolling, and safe labels in the frontend while native widgets own graph rendering. If the current widget cannot support an aspect directly, use a focused composition over existing surfaces and document the limitation; do not silently replace the native chart.

### 6.6 Bounded work and lifecycle

Extend one existing authoritative request/inspection projection with atomically correlated metadata. Preserve its retention/eviction/session ownership; share immutable component collections where possible rather than storing separate copies for the header and dialog. Do not persist prompt bodies, provider wire bytes, signed replay, or full conversation text for this feature.

Capture metadata once per final request through existing preparation/observation, reusing source lengths/segments and cached canonical tool metadata. Rounding/serialization attribution may require small preparation-local bookkeeping; release it after creating the size-only snapshot. Do not repeatedly scan full conversation text on each event, render, or modal open.

Render visible rows and cache layout by snapshot/width. Do not allocate a terminal buffer proportional to all conversation text or full off-screen chart height. Test the actual native-widget behavior against a large metadata inventory. If a metadata count must be bounded beyond existing request limits, preserve the omitted contribution in a labeled aggregate with exact total and item count; never silently truncate usage.

Keep all model/tool/event processing on the established execution path while the modal is open. Closing it only ends presentation. Do not hold execution locks across rendering or awaiting modal completion. Propagate cancellation and release UI queue tasks on shutdown.

## 11 Security/Permissions

This is metadata-only inspection of content already admitted to the user's session. It adds no execution or mutation authority and requires no new approval flow. Existing policy remains authoritative for any later user action outside the dialog.

Treat paths, tool names, and source labels as untrusted display data: sanitize controls, bound lengths, and use current safe Unicode rendering. Keep credentials, prompt/memory bodies, signed reasoning, encrypted replay, and provider wire payloads out of new events, logs, durable projections, and modal details. Private replay may contribute a named size-only amount. Do not infer hidden prompt contents or load external sources to improve labels.

## 12 Observability

Reuse existing request IDs, preparation/usage events, context inspection, and structured diagnostics. A captured snapshot explains which request/model/estimator the values describe. Record bounded metadata availability/reconciliation failures through the existing diagnostic path; an inconsistent breakdown must not appear complete.

The command itself follows existing command telemetry and cancellation. Do not emit an artificial tool activity or model request for local inspection. Do not flood the event log with row navigation or per-frame chart state. Performance evidence must distinguish measured timings/allocations from source-based expectations.

## 13 Migration/Compatibility

New inspection metadata is optional on existing records; old sessions remain readable and show unavailable detailed accounting until a new primary request is prepared. Avoid a durable migration or historical backfill.

Keep existing command meanings and normal modal sizes intact. Existing provider admission estimates and request content remain unchanged; only correlation of the primary context indicator is corrected where auxiliary requests previously displaced it. Cumulative usage/cost/cache accounting is unaffected. Original-frontend text output uses the same host data; headless execution gains no terminal dependency.
