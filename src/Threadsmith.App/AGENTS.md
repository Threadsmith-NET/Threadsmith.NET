# AGENTS.md — Threadsmith.App

> **Scope:** Process entry point and composition-root startup phases.

## Purpose

Coordinate Threadsmith startup without concentrating subsystem construction, policy, resource ownership, and terminal execution in `Program.Main`.

## Ownership

- `Program.cs` — ordered top-level orchestration and compatibility entry points only.
- `CommandLineParser.cs` — side-effect-free host argument parsing, including informational `--help` and `--version` switches used by installed-layout verification; MCP-only confirmation flags are host switches only when `--mcp` selects management mode.
- `ConfigurationBootstrap.cs` — normalized configuration paths, bounded ordinary layering that excludes secret values, a repository-excluding trusted machine/user/environment view, compiled defaults, and first-launch scaffolding.
- `HostFoundation.cs` — event, persistence, telemetry, semantic engine/refresh lifetime and deferred publication routing, process, tool, compiled static-secret provider registration, extension-capability, and repository-memory persistence foundations with reverse-order async disposal.
- `ModelComposition.cs` — provider catalogs, migration, authenticated host-owned Codex metadata contribution, repository-over-user startup selection, host-owned active-model state, request-bound provider switching, offline fallback, and owned application-lifetime HTTP/OAuth resources.
- `AgentRoleModelConfiguration.cs` - strict startup binding for trusted role provider/profile/reasoning preferences.
- `ApplicationComposition.cs` - evidence/conversation context, compaction/retrieval, session, repository, mutation, validation, parent-run approved-plan mutation preparation, model-callable delegation for all six roles, governed skill catalog/workflow/tool registration, and shared TUI/headless command-dispatch composition.
- `IntegrationComposition.cs` — optional extension startup plus application-lifetime MCP manager/transport/OAuth composition.
- `ShellRunner.cs` — interactive/headless projection, exact `--mcp` routing, and process-global cancellation registration.
- `Threadsmith.App.csproj` — executable references, configuration-example deployment, explicit flattening of every owning project's prompt assets into `prompts/`, and manifest-controlled `ThreadsmithDocs` deployment; canonical release assembly is owned by `eng/release/`.

Foundation composition supplies `write_file` with the existing conversation store and one repository-bound folder configuration. Tool-state rebinding updates that configuration before repository-open completion. `tools:writeFile:allowedFolders` defaults to `.inbox`; ordinary higher-precedence lists replace lower ones, and repository settings explicitly may select outside absolute output folders.

## Local Contracts

- Application composition owns one embedding generator and hybrid retriever, shares explicit repository memories across tools/commands/context, captures effective bounds per operation/turn, and rebinds memory persistence and options with repository lifecycle. Dispose retrieval and inference resources with the application; log verified migration backup paths. Repository-open memory migration and capacity eviction are the final commit callback inside the serialized lifecycle transition, after other service rebinding and session preparation succeed and before the new session is activated. Prepare memory options without publishing them; publish options and persistence only after their commit. Rollback must not migrate or evict either repository. A failed final callback revokes the prepared session and marks its catalog entry unavailable; cleanup failures retain both errors and report any durable status that could not be updated.

- `Program.Main` reads as the startup sequence; move cohesive phases into descriptively named files when doing so clarifies ordering, testability, or resource ownership.
- Startup eagerly creates exactly one deployed prompt loader from `AppContext.BaseDirectory` before prompt consumers are composed, then passes that immutable instance through constructor injection. Missing or invalid catalog content fails before provider/tool activity; no consumer receives an override or fallback seam.
- Phase state is immutable where practical. Resource-owning classes explicitly dispose in reverse dependency order and clean up partial initialization failures.
- Configuration parsing and command-line parsing remain independently testable and avoid startup side effects. Malformed JSON configuration fails startup with exit code 2 and one concise actionable file/parser-location message on standard error. The process entry boundary catches every otherwise-unhandled ordinary exception, emits one bounded single-line message without a stack trace, and returns a nonzero exit code; cancellation returns 130. Startup compiles `tui:showOperationDurations=true` into the normal layered configuration; TUI binding takes one immutable effective snapshot and malformed values warn while recovering to that default.
- Bind `agents:roleModels` from trusted configuration only. Reject legacy `agents:roleProfiles`, unknown exact role/field names, malformed or unavailable profiles, provider mismatch, and unsupported reasoning at startup. Omitted reasoning uses the profile default. Build both the role catalog and its dispatcher without repository overrides, including same-ID endpoint changes, and require user-owned or higher credential authority for those routes. Pass one immutable policy into model-requested child selection; do not read raw configuration in the scheduler. Role edits require restart and have no TUI editor.
- Compose `MutationProposalApplication` directly into the execution orchestrator for every model catalog. Implementation and correction use the parent run and ordinary session model settings; role-model configuration applies only to requested children. `delegate_agents` is the sole subagent launch entry point and requires model-origin invocation metadata plus the exact parent tool snapshot. Preserve exact-diff approval, transactions, validation, and corrections. `/agents <id>` and headless commands inspect/cancel durable state; neither inspection nor resume starts delegated work.
- Authenticated Codex startup discovery passes one bounded token through credential loading or refresh and metadata-cache loading because the shared model `HttpClient` intentionally has no global timeout. Optional refresh, network, response-validation, and timeout failures recover as unavailable Codex authentication so other configured providers can still start.
- Credential-bearing web-search provider settings and network-host allowlists come only from the trusted configuration view; repository, session, CLI, and repository secrets files cannot override them. Only that machine/user trusted view may set `tools:runProcess:requireApproval=false`; repository configuration cannot remove process approval and may reimpose it by listing `run_process` in effective `tools:requireApproval`. Because the ordinary tool pipeline uses fail-closed non-interactive approval, any effectively approval-required `run_process` is withheld from conversation. Tool registration and invocation contexts must use the same executable-allowlist resolver so an advertised shell is policy-authorized; the highest-precedence executable array replaces lower-layer arrays instead of retaining their unmatched numeric entries.
- Static secret providers are compiled in fixed environment → repository → user order. Repository secret JSON and the complete normalized `THREADSMITH_secrets__...` environment subtree stay outside ordinary and repository-excluding `IConfiguration`; only `EnvironmentSecretProvider` resolves an exact compatible environment value. Minimum source trust prevents repository values from satisfying managed hooks, MCP bootstrap, and private NuGet credentials. Managed hook references still come only from the repository-excluding trusted configuration view. MCP hook targets pin profile, server, schema digest, and tool id; extension hook targets pin generation and tool id, and invocation rejects a replaced registration.
- Comments explain phase intent, ordering, security boundaries, and non-obvious lifetime decisions rather than restating syntax.
- Interactive composition passes the normalized ordinary user-configuration path to the TUI so `/theme` can atomically persist `tui.defaultTheme`; theme persistence remains presentation-only and outside domain state. Interactive and headless surfaces consume the same composed dispatcher, including serialized active-session new/list/resume/clone/current commands, active-model list/current/select/reasoning and provider-authentication commands, model/session state, policy, projections, serial execution orchestrator, delegation coordinator/scheduler, skill catalog/workflow, checkpoint stores, and content-addressed execution artifacts. Repository open rebinds active models, tools, the shared MCP manager generation/auto-connect state, shared web-fetch authorization/retrieval narrowing limits, mutation policy, plan approval policy, native/Claude repository skill roots, and session lifecycle scope as one recoverable boundary only after facts, session registration, and completion publication succeed; lifecycle rebinding is last and activates a fresh repository-bound session. Web-fetch pipeline definition bounds remain fixed at repository-excluding trusted ceilings while authorization and retrieval use the rebound effective limits. Fresh-message URL authority is minted only from the raw submission after its durable message id exists and only when schema-3 consent plus effective `web_fetch` availability hold; run-completion observation revokes it. App composes UserAllowedNetworkHostStore from paths.UserConfiguration only; repository or layered configuration cannot redirect the store. App owns the application-lifetime serialized direct-fetch approval router: TUI attaches the sole interactive handler plus its URL-free process-local lifecycle sink, headless leaves it unattached and fails closed, and prompt details/outcomes never enter the shared durable domain stream. A `RunCompleted` subscription checkpoints durable selector metadata and usage before the turn is reported complete. Per-request model fallback is wired back through the same `ActiveModelSelectionApplication` used by `/models`; the composition-only deferred delegate breaks the session/lifecycle construction cycle without creating a second selection authority. A binding failure restores every service, including fetch limits, to the prior repository. Agent scheduler disposal precedes transactional-workspace disposal so shutdown first stops child admission and joins active children. The one-time router breaks only the construction cycle and never owns workflow state.
- Application composition registers `delegate_agents` only after model dispatch, context/instruction assembly, the tool pipeline/registry, usage projection, scheduler, and delegation coordinator exist and a configured profile satisfies the child request's capability and capacity requirements. Runtime selection rechecks the actual request with frozen assignment sensitivity. The tool registration is removed before those dependencies are disposed. Ordinary roles combine a system-prompt amendment, selected model, and eligible tools; their arbitrary final bodies are stored in `AgentRunOutcome.Response` with separate host role/model/status metadata, not parsed or promoted to verified findings. Empty replies may complete; transport failure, cancellation, security, and actual model capacity remain enforced. Trusted `agents:delegation` settings and active scheduler/tool/transport/result controls remain host-owned; repository configuration and model arguments cannot change them.
- Foundation composition owns one semantic-refresh coordinator and disposes it after the semantic lifecycle observer but before the engine registry. A one-time deferred publication router connects that coordinator to `SessionApplication` after construction; every submitted model request awaits freshness before allocating run identity, cancellation, budget, steering, registration, messages, model work, or tools, while refresh commands route through the same coordinator.
- Execution composition supplies plan sanity checks with the active workspace baseline before plan review/auto-approval; repository root, trust, and prohibited paths come from that rebound baseline rather than immutable startup configuration. It snapshots the loaded semantic project inventory, calculates the approved plan's affected project graph, and passes one resolved effective `validation:stages` list into both authoritative mutation validation and interactive validation-status presentation. The default stage list is `semantic`, `compile`, `diagnostics`, and `tests`; explicitly narrowing `validation:stages` controls which process-based build or unit-test stages execute.
- Application composition uses an unbounded budget for ordinary conversation because cancellation, tool-call accounting, per-tool timeouts, output accounting, and user-controlled budgets govern those runs; `execution:maxModelRounds` and `execution:maxPlanningToolRounds` both default to `0` and are only positive opt-in separate cutoffs. Each mutation-proposal operation receives a fresh configured execution-budget scope, never a process-lifetime quota. Application composition supplies model resolution to context assembly but does not bind a shared `context:maxTokensPerRequest` cap. Configured profile `ContextWindow` minus that profile's effective `RequestOutputTokenReserve` owns each request's governed input budget; provider `MaximumOutputTokens` remains a distinct hard capability. The assembler's compiled maximum is fallback-only when no configured model exists. Active-turn pressure remains owned by the active main profile; optional trusted `context:activeTurnCompaction:profileId`, `summaryBudgetTokens`, and `modelOutputBudgetPercent` values are read only from repository-excluding user/machine/host-owned configuration. The profile ID resolves and dispatches only through that trusted catalog/provider snapshot and routes candidate requests through its independently configured summary profile, while omission preserves the active main profile fallback. Repository-only profiles and repository provider/model/endpoint overrides never enter that auxiliary snapshot, repository configuration cannot widen summary budgets, and candidate provider credentials require user-owned-or-higher secret authority so repository secret stores cannot satisfy or replace them.
- Foundation composition registers workspace-owned Git queries and DotNet-owned inventory behind Core boundaries before constructing their Tools adapters; their lifetimes match the shared tool registry. Repository text search receives the shared tracked process manager and resolves app-local `tools/rg(.exe)` ahead of the source-development `PATH` fallback for bounded ripgrep acceleration. Release packaging stages that app-local executable; source development may populate the verified ignored `artifacts/dev-tools/<rid>/stage` cache through `eng/Stage-DevelopmentRipgrep.ps1`, and `Threadsmith.App.csproj` copies the executable plus license/source evidence into build and publish outputs without making ordinary builds network-dependent.
- Foundation composition derives the parallel-tool enabled state and maximum-concurrency ceiling from repository-excluding configuration; effective repository-layer values may only disable parallelism or reduce that ceiling.
- Foundation composition constructs the Validation facade over the shared tracked process manager, supplies only repository-excluding trusted named HTTPS advisory sources and logical credential references, and registers all seven typed adapters in the same interactive/headless tool registry.
- Skill startup discovers native metadata only from maintained/machine/user/repository plus trusted organization locations and separately discovers bounded Claude-style frontmatter from explicit user/repository `.claude/skills` roots; `CompatibleSkillCatalog` then projects both formats through the same verifier, external policy, workflow, command, headless, and `invoke_skill` boundary; repository configuration may disable repository discovery but trusted signers/allowlists/enablement/revocation come only from repository-excluding configuration and the user skill-policy file. The workflow orchestrator receives current session phase/trust/workspace facts from the durable projection for every restore/action boundary. The compiled host-owned `invoke_skill` tool is registered with a dedicated built-in activity source identity so nested declared tools do not wait behind their parent workflow's source lease; it remains registered for the application lifetime and is removed before skill workflow disposal.
- `Threadsmith.App.csproj` copies the curated `ThreadsmithDocs` bundle with root project/legal files and its source-relative `docs/` hierarchy to build and publish output without implementation plans, feature proposals, or internal release-readiness assessments. Docs-help skill tool contexts are rebound from the opened repository to that application-owned root before entering the central pipeline.
- Persistence startup runs schema initialization/migrations, artifact initialization, redaction audit, then one configured retention pass in that order. Retention is not a background timer.
- Release publishing must not copy scripting-worker runtime files from framework-dependent intermediate output paths; `eng/release/` explicitly publishes and stages the app and worker apphosts for the same RID, and composition prefers the colocated worker apphost over the development-only DLL fallback.
- MCP composition selects SDK-backed stdio, SSE, or streamable-HTTP transport and constructs one application-lifetime `McpManager` before the dispatcher, so trusted auto-connect, repository transitions, shared TUI/headless commands, and shutdown use the same authority. Imported tools are published to the shared tool registry for the connection generation, then successful connect emits `McpConnected`; capability-backed hook adapters are registered before manager startup. Optional connection failures, including profile-local startup timeouts and malformed OAuth cache state, are nonfatal. SDK and token-store types remain behind MCP-owned boundaries; OAuth-enabled HTTP profiles receive host-owned interactive/headless browser and callback adapters plus a logged, user-owned per-profile secret cache. Automatic connection attempts suppress OAuth authorization UX. Any `--mcp` action routes to machine-oriented management before optional extension composition regardless of `--tui`; headless OAuth instructions use standard error so the management result remains the only standard-output JSON value.

- Bind one restart-scoped `tools:codeExplore` operational snapshot and pass it to the semantic service, tool and formatter; ordinary main/child registration paths share it while keeping their own visibility and actual model capacity.

## Work Guidance

- Resolve global `context:activeTurnCompaction:profileId` and optional supported `reasoningLevel` once from trusted configuration. Pass the same candidate descriptor to the main loop and ordinary child runner factory. Configured candidates use trusted provider dispatch and provider instructions; role routing cannot override them. With both settings omitted/null, each loop uses its own active model and reasoning. Reject a reasoning override without a profile. Keep task-model selection, pressure triggers, and existing summary budgets independent.

- Preserve startup order: parse → paths/configuration → foundation → models → hook adapters → MCP manager/auto-connect → applications/dispatcher → `--mcp` shell or optional extensions → ordinary shell.
- Keep provider SDK, MCP SDK, terminal-library, and persistence implementation types within their existing composition boundaries.
- Do not shorten owned `HttpClient`, event subscription, semantic workspace, mutation coordinator, agent scheduler, skill workflow/tool registration, MCP adapter, or cancellation-source lifetimes during refactoring.

- Approval policy composition binds both services to the active repository configuration. Plan policy uses only repository storage; do not compose a user-owned plan-trust store. Session selections are in-memory overrides and never rewrite saved settings.

## Frontend selection

`InteractiveFrontendKind` is the startup source of truth: no switch means `None`, bare `--tui` and `--tui=tuikit` mean `TuiKit`, and `--tui=original` means `Original`. The former `--tui=pretty` spelling and all duplicate/empty/unknown selectors fail before startup. `UseInteractiveTerminal` is a derived compatibility property. MCP/authentication retain their existing precedence and do not construct a terminal backend. `InteractiveFrontendRunner` composes identical coordinator dependencies for both frontends; only the selected TUIKit path constructs and owns its retained terminal loop.
