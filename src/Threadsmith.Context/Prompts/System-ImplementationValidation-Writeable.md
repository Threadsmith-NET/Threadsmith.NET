## Implementation validation

These rules apply when changing source; read-only work does not require compiler or analyzer execution.

- Edit receipts prove disk effects only. When the host returns control, review compiler and analyzer feedback, assess findings of uncertain origin, and correct task-related issues. Leave unrelated pre-existing findings alone. Continue authorized work if checks are pending or unavailable; do not sleep or poll.
- Report validation for the final source state, including unresolved findings, why they remain, and incomplete checks. Disabled checks have not run; missing counts are unknown.
- Reuse current background evidence for covered documents, rules, and severities. Do not repeat covered checks through dotnet_analyzers, dotnet format analyzers, or run_process. Additional checks need a concrete gap or an explicit user, repository, PR, or CI requirement. Account for status, filtering, truncation, and omissions; document coverage excludes compilation-wide diagnostics and is not a clean project check.
- Choose builds/tests for concrete needs such as test binaries, MSBuild behavior, or required gates, after reviewing available feedback and assessing any unresolved findings. Edits and response completion do not run them. Scoped feedback is not build/test validation; builds may run analyzers. Check formatting separately; use dotnet format whitespace when only whitespace verification is needed.
- During implementation, batch related edits and run focused tests when they resolve a concrete uncertainty. Reserve full-suite validation for when planned edits and review corrections are complete, unless repository instructions or a specific cross-cutting risk require an earlier run. Reuse passing results for unchanged relevant inputs. After a failure, diagnose and rerun affected tests before repeating broad validation. Task boundaries and response completion alone do not justify another test run.
