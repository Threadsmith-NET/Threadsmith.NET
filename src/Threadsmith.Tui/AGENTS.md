# AGENTS.md — Threadsmith.Tui

## Purpose

Adapt the shared interaction layer to the conversation-first PrettyPrompt/Spectre.Console terminal frontend.

## Ownership

- PrettyPrompt multiline composer, buffered active-run key lease, Spectre.Console output adapter, serialized console ownership, and native-scrollback behavior.
- Width-aware shared-Markdown layout, Unicode terminal-cell measurement, semantic-role-to-style mapping, safe source rendering, and capability-gated redirected raw source.
- Immutable theme/style data, terminal-native system defaults, four compiled themes, layered configured-theme catalog loading, active theme selection, atomic user-default persistence, and safe PrettyPrompt/Spectre.Console adapter resolution.
- Composer-adjacent session-status formatting and placement plus source-compatible `ConversationalShell`, `TuiPresenter`, and `TuiController` facades over `Threadsmith.Interaction`.

## Local Contracts

- Ordinary terminal output is the transcript. Do not enable application mouse reporting or replace native scrollback selection.
- PrettyPrompt owns only active composer editing, wrapping, clipboard paste, and cancellation. Preserve submitted text exactly, including leading/trailing whitespace and line breaks.
- The composer has no completion source. Do not reserve completion-pane rows: multiline input must scroll only at the bottom of the visible window.
- `Ctrl+V` paste must enter as a complete clipboard operation; do not replay pasted text as synthetic per-character events.
- Mouse selection and terminal keyboard mark mode must copy any prior input or response with the terminal's normal `Ctrl+C` behavior.
- PrettyPrompt and Spectre.Console types remain inside this project and its adapter tests. Flush the active Spectre output writer before releasing the serialized console gate so review/status text is visible before PrettyPrompt begins its next read. `PlanProposed` and `MutationSetProposed` are lifecycle boundaries that end transient activity before their sequential review prompts can acquire the gate.
- Rendering call sites consume `PresentationTextRole`/`PresentationTextSegment`, never literal colors or terminal markup. The compiled `system` theme inherits terminal foreground/background; missing colors fall back through `Default`, while stable system semantic decorations survive unless the exact role explicitly overrides them. All built-ins keep ordinary transcript/composer backgrounds terminal-native, reserve backgrounds for actual highlights, and give the composer prompt and transient `THINKING` indicator distinct foreground-only roles. `NO_COLOR`, redirected output, or capability-limited terminals suppress all styling without changing words or markers.
- `Threadsmith.Interaction` owns answer collection, Markdig parsing, validation, control neutralization, event projection, and ordered presentation items. This project consumes the closed `MarkdownDocument` and semantic presentation batches, performs only width/layout/rendering work, and serializes them through the console gate. Cancellation can reject only pre-gate batch admission; an admitted batch completes non-cancellably. `THINKING` ends immediately before buffered output becomes visible.
- Live event batches preserve ordered plain text while assigning dedicated roles to user/assistant text, reasoning markers, tool outcomes, plan lifecycle headers/bodies, host path links, validation outcomes, added/removed diff lines, and stable Markdown semantics.
- Theme definitions are loaded whole from each configuration provider before case-insensitive id replacement; numeric array positions never merge fields across layers. Theme ids, colors, and decorations are bounded and validated before reaching Spectre.Console. Raw ANSI/OSC/control characters are not accepted as theme data. Each invalid configured theme is omitted independently while valid siblings remain selectable, and the interactive startup prints a bounded sanitized warning naming the rejected theme and reason. An unknown configured default is reported separately and selects the built-in `system` theme; catalog-wide bound failures still fail closed to `system` with an explicit warning.
- `ConversationTranscript.Apply(IDomainEvent)` in `Threadsmith.Interaction` is the single live append boundary. The TUI never reparses events or raw arguments; it renders the ordered semantic batches it receives. Subsystems publish host-owned domain events and never write directly to the terminal.
- `InteractionEventDispatcher` batches streamed events before output. Do not add a frontend event projector or render model chunks through a character-level redraw loop.
- The fixed shared command catalog contains `/open`, `/trust`, `/help`, `/new`, `/resume`, `/clone`, `/models`, `/auth`, `/mcp`, `/reasoning`, `/semantic_refresh`, `/thinking`, `/tools`, `/code_explore_output`, `/code_explore_inspect`, `/fetch-authorize`, `/memory`, `/context`, `/agents`, `/skills`, `/plan-policy`, `/policy`, `/theme`, `/validation retry`, and `/quit`. `InteractionCoordinator` owns parsing and host-command coordination; the TUI contributes only presentation-local `/theme` behavior through fixed application composition. Unknown slash commands fail locally and never reach the model. All selectors return only stable option identities; they never manufacture approval or policy authority.
- Interactive startup opens the current directory when `--repository` is omitted. Explicit repository, trust, and solution CLI values bypass only their corresponding prompts. A valid remembered `solution.path` auto-selects after trust and prints a repository-relative notification; explicit `--solution` overrides and refreshes memory. Missing memory falls back to normal discovery.
- Before trust/open, startup asks through host-owned initialization commands whether an empty repository should be scaffolded. The composition root supplies the initial pre-runtime-storage `.threadsmith` existence snapshot so its default database cannot suppress the prompt; later `/open` operations use live state. Use a numbered Initialize/Continue selector only when neither `.threadsmith/` nor a supported solution/project exists; confirmation is local, decline is non-mutating, and TUI never performs filesystem scaffolding directly.
- Startup renders the ASCII product wordmark and `Forge better code, not slop.` followed by a blank line, then host-derived model/repository/trust/solution/semantic status. After selecting a solution, show a transient `Semantic confidence: Loading...` spinner until the host publishes its semantic completion fact, then clear the spinner and print the terminal confidence or `Unavailable` for a completed `None` result before showing the composer. Subscribe before repository loading so the confidence or completion result is never missed. Never render credentials or secret references.
- The composer prompt is the sanitized, bounded current repository directory name and changes only after a successful repository open.
- Trust and ambiguous-solution prompts use numbered highlighted choices with Up/Down and Enter. Cancellation fails closed.
- Selecting Cancel from a startup trust, trust-upgrade, or solution menu exits the application before showing or reading the composer. In-session `/open` cancellation keeps the active session and prompt.
- Repository trust exposes inspect-only, read, build, and mutation grants. Build trust warns that repository-controlled code may execute. Invalid or cancelled choices fail closed.
- Structured plans run host sanity checks before review; proposal rendering uses the shared guided lifecycle block, remains decision-neutral while durable approval provenance is pending, and interactive plan review is queued only from an `ApprovalRequested` event whose host-owned kind is explicitly `Plan`; action/display text never determines routing, and legacy unclassified events fail closed. `/plan-policy` may auto-approve valid plans according to the selected policy, but that renders plan-approval provenance and any available concise risk basis through the shared block, only starts governed mutation preparation, and never approves exact diffs or writes. Approving a structured plan starts its governed mutation-preparation pass when a repository baseline is available. Shared lifecycle blocks, including mutation proposal status and applied mutation notices, use unbulleted ` LABEL:` headers with one formatter-owned leading-space indent, and adjacent visible host lifecycle blocks render with exactly one presentation-owned blank line between them. The resulting preview always renders before either a sequential mutation-review prompt or host-authorized policy application; interactive diff projection is compacted to changed hunks with bounded unchanged context and presentation-owned hidden-line markers while preserving added/removed roles and durable canonical full-diff authority. Mutation preparation and generic correction blocks render attempt and correction-reason detail; applied mutation blocks render policy provenance, affected path, and any available concise plan-derived detail without replacing semantic-check validation evidence. When post-apply validation is configured without the semantic stage, render a validation-start `MUTATION:` block so compile/diagnostics/test waits are not silent. Structured lifecycle previews additionally render operation, source/destination, risk, and case-only status through the same shared projection. Plan approval alone never approves mutations. `MutationSetProposed` is review-ready: the TUI loads its exact staged set through typed session/mutation-set ownership and fails closed if that contract cannot resolve, without polling or depending on execution-checkpoint timing. Policy-auto-approved plans enter the same exact-diff path as manually approved plans. `/plan-policy` lists five plan policy descriptions, warns for trust modes, updates session state, persists every plan policy except `TrustSession` to repository settings, and identity-fences `AlwaysTrustRepo`. `/policy` lists five mutation policy descriptions, warns for trust modes, updates session state, and persists/revokes only `AlwaysTrustRepo`.
- Applying an approved mutation delegates to the shared execution apply-only command: it verifies or captures the durable pre-mutation baseline, records/reconciles write-ahead commit state, applies the exact diff, then resumes post-apply validation through the host boundary before reopening the composer so validation completion, terminal validation failure/cancellation/rollback, or correction status is visible with distinct success/error/warning wording. A correction refreshes controller staging to the new mutation and re-enters the sequential exact-diff review loop; new ordinary submissions are rejected while a correction review is active. Cancellation or transient failure retains the exact post-apply run guard and prints `/validation retry`; that command resumes the retained run and releases the guard only at a terminal or correction-review phase. The TUI does not sequence persistence/workspace/validation itself.
- Discarding a staged execution mutation rolls back private staging, clears the local staged-mutation review state, and cancels the owning run so the completion observer cannot leave the composer blocked or reject later submissions as stale correction reviews.
- Spectre.Console live display is not used concurrently with PrettyPrompt input. Background output cooperatively ends and reopens an empty PrettyPrompt interaction through the serialized console owner so it becomes visible without physical input; once any draft text exists, output remains queued until the draft is submitted, cancelled, or cleared back to empty. The transient reasoning spinner remains active through suppressed leading whitespace, ends once before the first streamed reasoning or visible answer output is appended, and does not restart over streamed reasoning. A streamed reasoning block begins after one blank line, without adding separators between its chunks. The next composer does not open until the run-completion transcript batch is rendered. Status-display failures propagate through the shell boundary; they are never discarded.
- While PrettyPrompt is inactive, active-run hot keys are collected only through the public serialized `BufferedPromptConsole` input lease. Standalone `Enter` requests one idempotent safe-boundary steering prompt and double-`Esc` cancels; every other key and multi-key typed/pasted burst is replayed to the next PrettyPrompt read. Do not add another console reader or bypass this owner.
- The session status surface is composer-adjacent, not permanently pinned: PrettyPrompt 6.0.4 has no public fixed-status API, and cursor-managed pinning would weaken native-scrollback guarantees. `Threadsmith.Interaction` assembles immutable host-derived `SessionStatusSnapshot` values immediately before each composer; the TUI reevaluates terminal display-cell width, omits lower-priority segments rather than wrapping, pads non-empty output to the measured window width, and emits nothing when output is redirected. The dedicated `SessionStatus` role defaults to terminal reverse video in every compiled theme so padding and text form one bar without literal color assumptions; style suppression removes inversion. `tui:footer:enabled=false` hides presentation without disabling provider usage accounting.
- Process cancellation is linked into the interactive shell; Ctrl+C cancels active work before the terminal and shared resources are disposed. Cancelling a transient activity display must terminate its refresh loop and release the serialized console gate even when the underlying operation is still pending.
- Structured validation projections render compiler diagnostics plus test pass/fail/skip totals and host-authored selection rationale; raw process output remains outside routine transcript rendering.

- `/hooks` is an additional host command that lists and inspects configured handlers, applies process-local enablement, targets one handler for tests, externally approves/revokes exact repository declarations, and queries bounded audit through shared commands.

## Work Guidance

- Keep interactive behavior in `InteractionCoordinator`; `ConversationalShell`, `TuiPresenter`, and `TuiController` are compatibility/composition facades only.
- Keep command routing, approvals, repository/session workflows, event projection, Markdown parsing, and status assembly out of this project.
- Serialize prompt reads and output so background events cannot corrupt the active composer.
- Validate interaction changes in a real Windows Terminal in addition to terminal-neutral automated tests.
