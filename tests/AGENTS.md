# AGENTS.md — tests/ (Test Projects)

> **Scope:** All test projects under `tests/`.

## Purpose

Provide automated verification of project-level contracts: dependency direction, configuration binding, and architectural invariants. These tests are the **build gate** — they must pass before any merge.

## Local Contracts

### Delegated roles and model routing

- Shared compaction-model coverage must keep task and summary profiles/providers distinct, verify global reasoning and summary workload across all six roles, preserve task-model provenance after replacement, and retain the no-global-profile fallback. Reject invalid/unsupported global reasoning or reasoning without a profile at startup.

- Inherited evidence is delivered verbatim before it can be summarized. Verify unchanged task/instructions, preserved original evidence IDs, exact retrieval after replacement, and unchanged history when compaction is disabled or fails.

- Structured tool-result regressions must include actual central-pipeline redaction and evidence storage, not only preformatted JSON text. Check that redacted connection strings retain valid JSON through the child envelope and retrievable evidence.
- Keep estimated fallback usage distinct from provider-reported token counts. An estimate above a profile output maximum must remain accounted without causing a per-response rejection; a real reported overrun still fails, preserving observed usage.

- Keep old calls without `agents[].role` compatible with Explorer. Exercise all six exact role values, malformed request fields, mixed-role joins, and arbitrary final bodies including text, JSON, whitespace, empty replies, and absent legacy role fields. Ordinary replies use `AgentRunOutcome.Response` and never require citation GUIDs, semantic grading, or response-format repair. Keep host status/identity/generation checks independent of body claims and test failure/cancellation payload clearing. Every ordinary role must reject process, mutation, workflow, and recursive delegation; `inherit` may retain only eligible network read tools. Keep actual approved mutation validation/correction and legacy structured-result compatibility tests separate.
- Verify trusted `agents:roleModels` startup parsing, rejected `agents:roleProfiles`, profile/reasoning defaults, invalid roles/fields/bindings, precedence, actual-request fallback, and provider dispatch from the same trusted catalog. Include a same-ID repository endpoint override and prove it cannot reroute a configured child or supply its credentials.
- Verify configured/effective provider/profile/reasoning, source, fallback, role, contract marker, runner version, and `Response` survive persisted inspection. Distinguish an empty ordinary reply from null/missing response in legacy structured checkpoints; do not infer findings from new response contents. Do not treat checkpoint loading as a delegated-loop resume API. Approved-plan resume remains part of execution orchestration.
- Opt-in live role assertions check completion/join, trusted routing, and read-only mechanics. Save responses and usage for manual correctness, utility, and efficiency review; missing concepts, unsupported claims, citation format, or empty content are not automatic response-quality pass/fail criteria.
- Approved mutation preparation and corrections must retain the parent run identity, ordinary session model/reasoning selection, visible reasoning, exact-diff approval, transactional boundaries, and bounded repair failures without emitting delegation lifecycle events. Cover cancellation/provider failure before staging and native-tool profiles without JSON-mode capability. `delegate_agents` must reject non-model callers before checkpoints or child execution while model-requested delegation still works.
- Exercise parent mutation requests with the real `ContextAssembler` so model capabilities and complete provider-wire capacity are checked before dispatch. Keep delegated-role routing/capacity tests separate from ordinary mutation preparation; see ADR-57.

### `Threadsmith.Architecture.Tests`

- **`DependencyDirectionTests.cs`**: Parses `.csproj` `<ProjectReference>` entries to enforce the allowed dependency graph. Fails fast on a wrong reference and does not rely on reflection over compiled assemblies.
- **`AppBootstrapTests.cs`**: Verifies extracted command-line parsing (including side-effect-free help/version switches) and bounded configuration layering without launching persistence, models, integrations, or terminal surfaces.
- **`RepoConfigTests.cs`**: Loads `.threadsmith/config.example` via `Microsoft.Extensions.Configuration` and asserts every supported repository configuration key is present.
- **`PromptAssetArchitectureTests.cs`**: Enforces the exact prompt constants/catalog/source/deployment/documentation bijection and verifies that the user-facing prompt reference has exact category placement and counts, required-versus-optional token lists, glossary links, and one definition for every declared placeholder.

### Adding new test projects

- Place under `tests/Threadsmith.<Name>.Tests/`.
- Use scope-appropriate names that describe the behavior or subsystem under test; do not name test projects after milestones.
- Use xUnit (consistent with existing test project).
- Reference only the projects under test, not other test projects.

## Work Guidance

- Architecture tests parse `.csproj` files directly — they do not depend on compiled assemblies.
- Linked-path confinement fixtures use directory junctions on Windows so tests run without elevated symbolic-link privileges; non-Windows fixtures use symbolic links.
- When adding a product project, update `DependencyDirectionTests._productProjects` and `_allowedGraph`.
- When adding a forbidden package constraint, update `_forbiddenPackages`.
- When adding a config key, update `RepoConfigTests._requiredKeys`.
- Size fixtures in proportion to the behavior under test. Prefer a small injected limit crossed by one, a few stable records, or one directly relevant file over production-scale trees, payloads, generated identifiers, or brute-force boundary searches.
- Unit tests must be hermetic and normally subsecond; three seconds is the hard ceiling for any individual test in the ordinary suite. A scenario that requires network access, an external service, an installed executable, ambient filesystem/source-tree state, or a longer runtime belongs in an explicitly categorized opt-in integration or stress suite.
- Coordinate async and concurrency tests with `TaskCompletionSource` using `RunContinuationsAsynchronously`, gates, fake time, or existing lifecycle events. Use small cohorts that positively prove entry/overlap, and keep real-time timeouts only as bounded failure diagnostics.
- Exact production-boundary and OS/runtime integration tests are valid and must not be mechanically downsized. Retain the real limit or integration when that boundary is itself the contract, and make the reason visible in the test.
- Every fixture that creates files, staging generations, processes, or other artifacts must own and release them. Cleanup must validate the exact normalized owned root and must refuse broad locations such as a filesystem root, repository root, user profile, or shared temporary parent.
